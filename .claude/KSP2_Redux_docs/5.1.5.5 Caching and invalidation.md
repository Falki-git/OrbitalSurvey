# Caching and invalidation

Running every patch against every asset takes time, so PatchManager does not do it on every launch. It caches the patched output and reuses it until something that would change the result changes. Understanding what counts as "something changed" explains why an edit sometimes does not show up until you force a rebuild.

## What is cached

PatchManager caches the final patched assets: the JSON after all patches in all passes have run. On a launch where nothing relevant has changed, it loads that cached output instead of running your patches again. This is invisible when it works and confusing when it does not, which is the reason this page exists.

## Inspecting the cache to see the final result

The cache is not just an optimization, it is the single most useful debugging artifact PatchManager produces. It lives in a folder called `pm_cache` in the game's working directory, next to `pm_summary.log`, and it contains the exact final state of every patched asset. Where the [summary](/doc/reading-the-summary-8ahmOdWbza) tells you *what happened*, the cache shows you *the result*: the asset as the game actually loads it, after every patch from every mod has run.

Inside `pm_cache` you will find:

* `inventory.json`, PatchManager's own bookkeeping. You can ignore it.
* One `.zip` archive per patched label, named after the label. Parts, for example, are under the `parts_data` label, so their archive is `pm_cache/parts_data.zip`. Each kind of content has its own archive.

Open one of those zips and you get one file per asset, named by the asset's id, each holding that asset's final patched JSON. So `parts_data.zip` contains an entry for every part, named with the part id, holding the part's data after all patching.

This gives you two things that are hard to get any other way.

**Checking the final state of your patches.** Open the archive for the label you patched, find your asset's entry, and read the JSON. That is ground truth. It reflects your change *and* everything every other mod did to the same asset, in final form. It is the most direct way to confirm a value actually landed and was not overwritten by a later patch, which is the one thing the summary cannot show you (the summary says your patch `APPLIED`, but not what the value ended up as after the patches that ran after yours).

**Finding the ids of other assets.** The entry names in an archive are the asset ids. When you need the exact id of a part to put in [`:Named`](/doc/targeting-assets-8eefHSmg4w), browse `parts_data.zip` and read the names off the entries. This is a reliable, complete list of real ids, which beats guessing or hunting through game files.

Two caveats. The cache reflects the most recent build, so if it was served rather than rebuilt (see below) it shows the last built state, not necessarily your newest edits, force a rebuild to refresh it. And the JSON inside may be minified rather than pretty-printed, so run it through a formatter if you want to read it comfortably.

## What triggers a rebuild

PatchManager rebuilds the cache when any of these change between launches:

* **Your patch files.** PatchManager hashes the `.lua` patch files. Edit a patch and relaunch, and the changed hash forces a rebuild, so ordinary patch development just works.
* **The set of loaded mods.** Installing, removing, enabling, or disabling a mod changes the mod set and rebuilds, since a different set of mods can patch differently.
* **Config values you have tagged as patch-affecting.** This is the one that is not automatic, and it is covered next.

If none of these changed, the cache is reused, and patches do not run.

You can also force a rebuild by deleting the `pm_cache` folder, or by toggling the relevant setting in the settings menu for patch manager and restarting the game.

## Config values do not rebuild on their own

A [config](/doc/config-integration-aTM54Tfqkz) value that your patches read is not, by default, part of what the cache watches. If a player flips a setting your patch consults, but nothing else changed, PatchManager will happily serve the old cached result and your patch will not re-run to honor the new setting.

You fix this by tagging the config entry so PatchManager watches it. Tag it with `PM.InvalidatesOnChange`:

```lua
Config:Define("Tweaks", "BuffHeavyEngines")
    :Type(Boolean):Default(true)
    :Tag(PM.InvalidatesOnChange)
    :Bind()
```

PatchManager snapshots the values of every entry carrying this tag. When a tagged value differs from the snapshot on the next launch, it rebuilds. So tag exactly the settings your patches read.

## Tag deliberately, not everything

Tagging is a trade-off. A tagged setting that changes forces a full rebuild, which costs the time the cache was meant to save. So tag the settings that genuinely change patch output, and leave alone the ones that do not (a setting that only affects runtime behavior, not what your patches produce, does not need the tag). The goal is that the cache rebuilds exactly when the result would differ, and not otherwise.

## When a change is not showing up

If you changed something and the game does not reflect it, the cache is the first suspect:

* Edited a patch file but see no change: confirm you saved the file. A saved edit changes the hash and rebuilds.
* Changed a setting but see no change: the setting probably is not tagged with `PM.InvalidatesOnChange`, so the cache was reused. Tag it.
* Still stale: the [summary](/doc/reading-the-summary-8ahmOdWbza) reflects the most recent run. If it does not show your patch, the cache was served rather than rebuilt.
* If all else fails: Delete `pm_cache` and it will be rebuilt on the next run

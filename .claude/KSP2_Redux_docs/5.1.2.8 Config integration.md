# Config integration

A patch can read settings the user controls. The `Config` global is your mod's own settings namespace, shown to players in the settings menu and persisted to a config file. Use it to make a patch optional, to expose a tunable number, or to let players pick from a set of choices, without them editing your Lua.

`Config` is available to every patch script alongside `PM` and `J`.

## Defining an entry

You declare an entry with `Config:Define(section, name)`, chain a few descriptors, and finish with `:Bind()`. Binding returns a live handle you read through:

```lua
local buffEngines = Config:Define("Tweaks", "BuffHeavyEngines")
    :Type(Boolean)
    :Default(true)
    :Desc("Increase the thrust of heavy engines.")
    :Tag(PM.InvalidatesOnChange)
    :Bind()
```

Every example on this page carries `:Tag(PM.InvalidatesOnChange)`. That tag is what makes PatchManager rebuild when the setting changes, which any setting your patches read needs. It is explained under "Making a setting rebuild patches" below. Add it to every config entry a patch reads from.

`Define` takes a section and a name, which is how the entry is grouped and labeled in the settings menu. The following builder members are then used to fill it out:

* `:Type(...)` sets the value type. The built-in types are the globals `String`, `Integer`, `Double`, `Boolean`, and `Color`. This one is required.
* `:Default(value)` sets the value used on first launch, before the player changes anything.
* `:Range(min, max)` constrains a number to a slider. Optional extra arguments set the slider step count and number format.
* `:Values({...})` constrains the value to a fixed set of choices.
* `:Desc(text)` sets the description shown in the settings menu. `:NameLoc(key)` and `:DescLoc(key)` set localization keys instead, for translated text.
* `:Tag(name)` attaches a metadata tag. The one tag that matters here is covered below.
* `:Bind()` finalizes the entry and returns the handle.

Entry definition is idempotent. If you define the same entry in multiple Lua files for your mod, it will not create multiple config entries, and if the form of all the entries is the same then it does not matter which one runs first. This means that you are safe to define config handles in a [library](/doc/sharing-lua-with-require-hXbW2HK8Ep) file for your mod.

## Reading and writing the value

The handle has a `value` field. Read it to get the current setting, assign it to change the setting (which is automatically persisted):

```lua
if buffEngines.value then
    -- the player has this turned on
end
```

If you only need to read an entry you defined elsewhere, `Config:Get(section, name)` returns a handle for an existing entry, or `nil` if it was never defined.

## Gating a patch on a setting

The most common use is switching a whole patch on or off. Read the value and feed it into [`:Requires`](/doc/gates-Zh2sLnyxZX) as a constant boolean:

```lua
local enabled = Config:Define("Tweaks", "BuffHeavyEngines")
    :Type(Boolean):Default(true):Tag(PM.InvalidatesOnChange):Bind()

PM.Parts:Patch("BuffHeavyEngines")
        :Requires(enabled.value, "disabled in config")
        :Named("engine_2v_methalox_mainsail")
        :Do(function(part) ... end)
```

When the setting is off, the patch is skipped and the reason shows in [the summary](/doc/reading-the-summary-8ahmOdWbza). You can just as easily feed a `Double` value into a calculation inside the callback, or use an `Integer` or a `Values` choice to switch behavior.

## Making a setting rebuild patches

Patches are [cached](/doc/caching-and-invalidation-QifFi4oev9). PatchManager builds the patched assets once and reuses the result, so simply changing a config value does not re-run your patches on its own. If a setting is meant to change what your patches produce, tag its entry so PatchManager knows to rebuild when it changes:

```lua
Config:Define("Tweaks", "BuffHeavyEngines")
    :Type(Boolean):Default(true)
    :Tag(PM.InvalidatesOnChange)
    :Bind()
```

`PM.InvalidatesOnChange` is a tag that marks an entry as patch-affecting. When a tagged entry's value changes, PatchManager rebuilds. Tag *only* the settings your patches read, so unrelated setting changes do not force a needless rebuild.

## Using another mod's config

`Config:Mod(modId)` gives you a read and write view over another mod's config, so a patch can react to a setting that belongs to a different mod. Don't use this for your own settings, use `Config:Define` and `Config:Get` as shown throughout this page.

## Config file location

Your mods config file location depends on whether or not it is a "standalone" Lua mod. If it is standalone, then the config file will be in the mods folder right next to your Lua file. If not then the config file will be in the root of your mod's folder next to its SWInfo manifest.

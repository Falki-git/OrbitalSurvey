# Shipping patches

Once your patches work locally, you package them as a mod so other people can install them. A patch mod is the same kind of mod as any other Redux mod. It just happens to contain Lua patches instead of (or alongside) a compiled assembly.

## The minimum

A shippable patch mod is a folder with:

* a `swinfo.json` manifest, and
* one or more `.lua` patch files anywhere inside it.

The manifest identifies the mod, this is what ones looks like and makes for a good copy-able template.

```json
{
  "spec": "3.0",
  "mod_id": "BetterParts",
  "name": "Better Parts",
  "author": "Your Name",
  "description": "Tweaks a handful of stock parts.",
  "source": "https://github.com/yourname/better-parts",
  "version": "1.0.0",
  "version_check": "https://raw.githubusercontent.com/yourname/better-parts/main/swinfo.json",
  "ksp2_version": { "min": "0.2.8", "max": "*" },
  "dependencies": [
    { "id": "SpaceWarp2", "version": { "min": "2.0.0", "max": "*" } }
  ],
  "conflicts": []
}
```

* `**mod_id**` is your mod's id. It is what `ModId` resolves to in your scripts and what other mods use when they declare a dependency on yours. Keep it a simple identifier-style name like `BetterParts`: start with a letter, then letters, digits, and underscores only. Keep it stable across releases: changing it makes your mod look like a different mod to anything that depended on it. Mod ids are matched case-insensitively.
* `**name**`, `**author**`, `**description**`, `**source**` are display text shown to users.
* `**version**` is your mod's version, using semantic versioning. Bump it on each release. `version_check` optionally points at a hosted copy of this file so the game can tell users an update exists.
* `**spec**` is the manifest format version. Use `3.0` for new mods.
* `**ksp2_version**` is the game version range your mod supports. `"*"` means no upper bound.
* `**dependencies**` lists other mods that must be present, each with a version range. If your patches only make sense with another content mod installed, add it here, and also declare it on the patch with [`:Needs`](/doc/dependencies-and-ordering-werp1yYh7P).
* `**conflicts**` is the mirror of dependencies: mods yours must not run alongside.

## A typical layout

```
BetterParts/
  swinfo.json
  patches/
    engines.lua
    tanks.lua
  lib/
    _shared.lua
  README.md
```

The `patches/` split is purely organizational. The underscore on `_shared.lua` keeps it from running as a patch on its own, so it can be a helper library that `engines.lua` and `tanks.lua` pull in with `require`. See [Sharing Lua with require](/doc/sharing-lua-with-require-hXbW2HK8Ep).

## Installing

Users install a patch mod the same way as any Redux mod: they place the mod folder into the game's `mods` folder. On the next launch, PatchManager discovers the `.lua` files inside it and runs them. There is nothing extra to enable.

For a quick personal tweak that you are not distributing, you can skip the mod folder entirely and drop a single `.lua` file straight into the `mods` folder. See [file layout and discovery](/doc/file-layout-and-discovery-vYcsLN5rtw). For anything you hand to other people, ship a real mod folder so it has a stable id, a version, and room to grow.

## Declaring dependencies

If your patches only make sense when another mod is present (you patch a part that mod adds), or must not run alongside a mod they would conflict with, declare that on the patch itself with `:Needs` and `:Conflicts` rather than hoping load order works out. See [Dependencies and ordering](/doc/dependencies-and-ordering-werp1yYh7P) and [Cross-mod compatibility](/doc/cross-mod-compatibility-Kprr92mfVd).

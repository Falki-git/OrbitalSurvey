# Parts

`PM.Parts` patches part definitions: pods, engines, tanks, decouplers, wheels, and everything else you place in the editor. It is the biggest typed module because a part is the biggest asset.

A part definition is a tree. The part has top-level fields (mass, `maxTemp`, `crashTolerance`, attach nodes, editor category). It holds a set of **modules** (`Module_Engine`, `Module_Deployable`, `Module_Drag`, and so on), each module holds one or more **data** entries (`Data_Engine`, `Data_Deployable`), and the data entries hold the actual numbers you usually want to change.

## Patching a part

`PM.Parts:Patch(name)` registers a patch against parts. Restrict it to specific parts with `:Named(...)`, using the part's id (`heatshield_2v_inflatable`, `eva_kerbal`, and so on). Inside `Do`, top-level fields are plain assignments:

```lua
PM.Parts:Patch("KerbalImpactToleranceFix")
        :Named("eva_kerbal")
        :Do(function(part)
            part.crashTolerance = 30.0
        end)
```

To reach a value nested in a module, use the module and data helpers below.

## Finding the field you want

A part has well over a hundred fields spread across its modules. This module documents the forms and the common edits, not every field. The full field list for a part, a module, or a data entry is in the `pm-parts.d.lua` stub, which surfaces as autocomplete and hover docs once you have [set up your editor](/doc/setting-up-your-editor-UScg880clw). When in doubt, type a dot and read what the editor offers.

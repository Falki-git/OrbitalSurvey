# Cross-mod compatibility

A patch rarely runs alone. The base game's patches, Redux's patches, and other mods' patches all touch the same assets. Writing a patch that coexists with that, instead of fighting it, is mostly a matter of using the tools from [Dependencies and ordering](/doc/dependencies-and-ordering-werp1yYh7P) deliberately. This page collects the practices.

## Lean on namespacing

Every patch id is `modId:patchName`, and the mod id is prepended for you. You do not have to worry about another mod using the same patch name as you, because the namespaces keep them apart. The one thing you control is keeping your own [mod id stable and identifier-safe](/doc/shipping-patches-8EnGXsVNKP), since everything else keys off it.

## Declare what you depend on, do not assume load order

If your patch only makes sense when another mod is present, say so with `:Needs`. Do not rely on the other mod happening to load first, and do not let your patch error against content that is not there:

```lua
PM.Parts:Patch("RetuneTheirEngine")
        :Needs("EnginePack")
        :Named("their_engine_id")
        :Do(function(part) ... end)
```

With `:Needs`, your patch runs only when `EnginePack` is loaded, and is cleanly removed (and noted in [the summary](/doc/reading-the-summary-8ahmOdWbza)) when it is not. The same applies to `:Conflicts` for a mod whose changes would fight yours.

## Prefer the default pass, order only where you must

The strongest thing you can do for compatibility is to leave your patch in the Default pass and Default bucket. That keeps you in the cooperative middle, where other patches can order around you. Grabbing `:Early():First()` to "make sure my change wins" is the opposite: it forces you to the front and makes you the patch everyone else has to work around. Reserve the passes for their real roles (collect early, finalize late) and order against specific patches with `:Before` / `:After` only when you have a concrete reason. See [The patch lifecycle](/doc/the-patch-lifecycle-bV7YhyoMv8).

## Patch the difference, not the whole thing

A patch that sets one field stays compatible with a mod that sets a different field on the same asset, because they do not collide. A patch that replaces a whole list or object stomps anything another patch did to it. So change the narrowest thing that achieves your goal:

```lua
-- Compatible: adds to the list, leaving other entries (and other mods' additions) intact.
node.UnlockedPartsIDs:Append("my_new_part")

-- Risky: replaces the whole list, discarding anything anyone else added.
node.UnlockedPartsIDs = { "my_new_part" }
```

Use the [list and object methods](/doc/working-with-json-fWfY8KrejF) (`:Append`, `:RemoveWhere`, `:Patch`) to make surgical changes instead of wholesale replacements when you can.

## Gate on what is actually there

When you patch a broad set of assets, guard the parts that might not apply to every one with [gates](/doc/gates-Zh2sLnyxZX). `:Has` and `:HasNo` keep your patch from assuming structure that another mod may have changed, and they report a clean skip instead of an error when an asset is not in the form you expected.

## Read the summary against a full modlist

The real test of compatibility is the [summary](/doc/reading-the-summary-8ahmOdWbza) produced with the other mods installed. It shows whether your patches applied, got removed by a dependency, or errored against content another mod changed. When you support a mod combination, check the summary with that combination present, not just your mod alone.

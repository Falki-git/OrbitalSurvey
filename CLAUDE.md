Guidance for Claude Code when working in this repository.

## Git rules

- **NEVER commit or push without the user explicitly asking.** Do not commit as part of
  completing a task; wait for a direct instruction such as "commit", "commit and push", etc.
- **NEVER commit directly to `redux/master` OR `redux/development`.** Both are protected
  integration branches; changes reach them **only by merging a feature/bugfix branch**, never by
  a direct commit.
- **Branch model (this project):**
  - **`redux/master`** — **the main branch for this repo.** Holds the *exact state of the
    currently released version*; nothing lands on it except a finished, published release
    (normally by merging `redux/development`). Never commit here directly.
  - **`redux/development`** — holds the not-yet-released code under active development. Cut from
    `redux/master`; the base for ongoing work. **Never commit here directly** — changes arrive
    only via merged feature/bugfix branches.
  - **Feature/bugfix branches** — **every feature or bugfix starts on its own new branch cut off
    `redux/development`.** Do the work there. When it's ready, the user will ask you to **open a
    PR against `redux/development`**; the branch is **merged back when the user says so**, and
    the user **merges manually**. Don't merge yourself.
  - **`master`** — a frozen archive of the original *pre-Redux* released codebase (the
    SpaceWarp-1.x version). Reference/history only; **not actively developed**. Don't branch work
    off it or commit to it. Note `origin/HEAD` still points here — it is *not* the working main
    branch; `redux/master` is.

## What this project is

This is the **Kerbal Space Program 2 (KSP2) Redux mod template** — a ThunderKit +
SpaceWarp2 based Unity project used to develop KSP2 mods. It is a *template*: it ships the
game's reference assemblies, the ThunderKit build pipeline, and a skeleton for one or more
mods. Each mod you build lives in its own folder under `Assets/` and is packaged by
ThunderKit into a loadable mod.

- **Engine:** Unity `6000.5.0f1` (Unity 6.5)
- **Modding stack:** ReduxLib (loader) → SpaceWarp2 (mod API) → your mod
- **Build/packaging:** ThunderKit (Unity editor pipelines) — NOT a plain `dotnet build`

> **Per-mod details live in [`.claude/mod_specifics.md`](.claude/mod_specifics.md).** That
> file describes the specific mod(s) currently under development in this repo — what they do,
> their folder name, entry point, gameplay/UI design, and any build/deploy notes. Read it
> before doing feature work. It is intentionally mod-specific; keep this `CLAUDE.md`
> mod-agnostic so it stays valid as mods come and go.

## The modding stack (load order)

```
BepInEx-style native loader
  └─ ReduxLib.dll            ← low-level loader, logging, message bus, config
       └─ SpaceWarp2.dll     ← mod API: GeneralMod/ISpaceWarpMod, assets, localization
            └─ SpaceWarp2.Game.dll / .UI.dll / .Sound.dll / .VersionChecking.dll
                 └─ YourMod   ← extends KerbalMod (default) or GeneralMod
```

A mod is a class extending `Redux.ExtraModTypes.KerbalMod` with three lifecycle hooks.
**Default to `KerbalMod`** — it's a MonoBehaviour, so you get the `Update` loop and direct
game references (like legacy SpaceWarp 1.x mods):

```csharp
using Redux.ExtraModTypes;

public class MyMod : KerbalMod {
    public override void OnPreInitialized()  { /* before assets/addressables load — register loaders */ }
    public override void OnInitialized()     { /* assets loaded; safe to touch game code */ }
    public override void OnPostInitialized() { /* all mods initialized */ }
}
```
- Extend `SpaceWarp2.API.Mods.GeneralMod` instead for a plain (non-MonoBehaviour) lifecycle
  object when you don't need the `Update` loop (this is what the ThunderKit scaffold defaults
  to for a new mod).
- Both provide `SWConfiguration` (IConfigFile), `SWMetadata` (guid/version), and
  `CreateHarmonyAndPatchAll()` for Harmony patching. For logging, use ReduxLib's per-class
  logger (see Conventions), not the `SWLogger`.

Each mod ships a **`swinfo`** manifest (authored as `swinfo.asset`, emitted as `swinfo.json`):
`mod_id`, `version`, `main_assembly`, `dependencies` (e.g. `SpaceWarp2 >= 2.0.0`),
`ksp2_version` range.

## Working with the KSP2 codebase (CRITICAL)

`Packages/KSP2_x64/Assembly-CSharp.dll` is the game. You cannot read it as text.

**To inspect game code, decompile with `ilspycmd`** (installed globally via `dotnet tool`):

```bash
export PATH="$PATH:$HOME/.dotnet/tools"
# List every type:
ilspycmd -l c "Packages/KSP2_x64/Assembly-CSharp.dll"
# Decompile a single type (preferred — fast, targeted):
ilspycmd -t "KSP.Sim.impl.VesselComponent" "Packages/KSP2_x64/Assembly-CSharp.dll"
```
Always prefer `-t <FullTypeName>` over decompiling the whole assembly. To find a type,
list with `-l c` and `grep`. Other game assemblies (`SpaceWarp2.dll`, `ReduxLib.dll`,
`UitkForKsp2.dll`, `SpaceWarp2.Game.dll`) decompile the same way. See
`.claude/ksp2_assembly_csharp_reference.md` for the namespace map and recipes.

> ilspycmd prints a "not using the latest version" notice to stderr — ignore it.

### Private game members (publicizing vs. reflection)
The shipped `Assembly-CSharp.dll` keeps its original access modifiers (private/internal).
A `publicize.bat` (NStrip) exists to produce an all-public copy, but:

- **NEVER run `publicize.bat`.** Whether to publicize is *exclusively the user's choice* — do
  not invoke it, and do not suggest running it as part of a task.
- **The publicizer is currently broken.** So the working approach is to **access private/
  internal game members via reflection** — that's how this codebase reaches non-public members.

## Conventions & gotchas

- **Don't edit generated files** (`*.csproj`, `*.sln`, `Library/`, `Temp/`, `obj/`,
  `Redux/`, `ThunderKit/`). They're regenerated by Unity/ThunderKit.
- **`Library/`, `Temp/`, `pm_cache/`, `Redux/Addressables/`, `Assets/StreamingAssets/`** are
  large/binary noise — exclude them from searches. Real source lives under a mod's
  `Assets/<YourMod>/` folder.
- KSP2 wraps Harmony as `0Harmony.dll`. Patch via `CreateHarmonyAndPatchAll()`.
- Building is done through **ThunderKit pipelines in the Unity Editor** ("Build for Editor",
  "Build for Player", "Deploy to Zip File" under each mod's `Pipelines/` folder), not from a
  terminal. Claude generally cannot drive the Unity editor; ask the user to run pipelines.
- **Logging:** create a logger per class that needs one via ReduxLib, not `SWLogger` or
  `UnityEngine.Debug`:
  ```csharp
  private readonly ILogger _logger = ReduxLib.ReduxLib.GetLogger($"<modname>|{nameof(MyClass)}");
  // or, from an instance context (ctor / lifecycle method):
  _logger = ReduxLib.ReduxLib.GetLogger($"<modname>|{GetType().Name}");
  ```
  Use the mod's name for `<modname>` so log lines are tagged `<modname>|<ClassName>`.
  (`GetType()` can't be used in a field initializer, so assign in the constructor there.
  Decompiled game code uses `Debug.Log*` heavily — that's the game, not you.)

## PatchManager Lua patches (Redux6)

Redux6 **does not expose a C# patching API for game content**. Changes to game content
(adding modules to parts, defining science experiments, missions, resources, etc.) are done
via **PatchManager Lua patches** — placed in a mod's `Copied/Patches/` folder so they ship
with the mod. The authoritative reference is the PatchManager section of the Redux docs at
`E:\GitHub\KSP2\_KSP2 Redux docs` (or <https://modding.ksp2redux.org> if the local copy isn't
accessible).

Key patterns:
- Patches are discovered by file under the mod's shipped `Patches/` folder and run in a
  well-defined lifecycle *after* the game's content loads — read C#-visible config values in a
  game-load message handler, not in `OnInitialized()`.
- `Config:Integer(section, key, default, description)` / `Config:String(...)` write values into
  the mod's `SWConfiguration` (IConfigFile) so C# can read them back and other mods can override.
- Typed module APIs exist for Parts, Missions, Planets, Resources, Science, Audio, and VSwift
  part variants.
